# 语义层怎么开发

语义层是本工具里唯一会花钱、会变、会判错的一段。它只处理规则判不了的段，其余全交给规则引擎。

## 一、为什么不做成「全篇送模型」

全篇送模型有三个代价：贵、慢、不可复跑。同一段文字跑两次得到不同结论，验收标准就废了。

现在的分工是：规则先跑（毫秒级、免费、结论固定），只把 `voice` 与 `syntax` 挑出的段送判，缺省十段，`--limit` 可调。

## 二、提示词在磁盘上

`src/language/sense-prompt.md`。查找顺序与契约一致：从当前目录往上找，找不到再退回编译期目录。改提示词不需要重编译。

提示词只有一问，别加第二问：**读者读完要做什么？如果他什么也不用做，就是 process。**

踩过的坑：第一版把「分条清楚的内部处置列表」判成 `reader`，因为模型把分条当成面向读者。于是补了两句——「分条清楚 ≠ 对读者说话」「判断标准只有一问」。A/B 对比过列表化版与原文一段版，确认列表化处置仍判 `process`。

改提示词后必须做这个 A/B：拿同一批段，改前改后各跑一次，人工核十条。只跑一遍看不出退步。

## 三、调用纪律

`temperature=0`，`max_tokens=300`，只接受 JSON。三个都不是可选项：

- `temperature=0` 为了可复跑；
- `max_tokens=300` 为了不让模型长篇解释，解释进不了判断；
- 只接受 JSON 为了解析确定。返回散文时降级为 `unknown`，理由取原文前一百二十字，**不猜、不重试**。

## 四、不依赖任何外部 SDK

`ureq` 直连 OpenAI 兼容的 `/chat/completions`。第一版想复用 `quanttide-agent` 的 LLM 调用，代价是这个工具装到别处以后语义层是死的——运行时依赖一个内部包，装成命令行工具后找不到。

自带最小 HTTP 客户端之后，`cargo install` 完就能跑。

## 五、`--json` 与 `--sense` 不并存

语义层结论不并进 JSON。理由是全量扫描的 JSON 要可复跑做基线对比，混入模型结论就不再可复跑。要看语义层就用人类可读模式。

## 六、凭据

环境变量 `LLM_API_KEY`／`LLM_MODEL`／`LLM_BASE_URL` 优先，其次本机 `~/.pi/agent/auth.json` 的 `deepseek.key`。密钥不落日志、不打进错误信息。取不到就以退出码 2 明确报错，不静默跳过——静默跳过会让人以为语义层跑过了。
