# 本地与云端：同一条入口，不写兼容层

一句话：**本地程序跟着平台模型适配，不是平台适配本地程序。**

## 一、两种做法的代价差在哪

**写兼容层**：本地程序保持原样——cron 表、钩子直接调函数、本地路径——再写一层适配让它也能在云上跑。那层适配是永久的，也是最先烂的：它同时被两个世界拉扯，谁改它都得同时理解两边。

**跟着适配**：本地程序从第一天就按平台模型写。云上能跑的东西，本地跑的是同一条路径。

`infra` 走后一条。归到哪只有一句：**本地和云端的分界在「谁调 `fire`」，`fire` 里面完全一样。**

## 二、怎么落进代码

`infra` 的表里只有 `trigger` 与 `run`。`trigger` 是带标签的枚举，`event` 与 `every` 两个变体形状对等——因为云端总线来的时候没有「周期」这个概念，只有「某个事件发生了，谁关心」；周期只是驱动方的一种投递方式。

三处由此而来。事件名不枚举——`pre-commit` 不校验是不是合法 git hook 名，一校验，总线上的 `release.published` 就成了非法事件名。周期串不解析——`0 3 * * *` 不翻译成「每天三点」，一翻译，换成 systemd timer 时语义就变了。`emit` 只打印不安装——它给的是驱动方那一行，不是又一层适配。

## 三、代价看得见

```text
$ qtfounder infra fire post-release
事件「post-release」没有订阅者        ← 退出码 0
```

它分不清拼错和「合法但没人订」，所以不能报错。**报一个假错比不报错更坏**——知道哪些事件存在的是驱动方，不是 CLI。

## 四、给改这段代码的人

这条风格不写下来就会被「修好」。AI 的默认是通用化，而兼容层长得就像通用化：「校验一下事件名」听起来是严谨，「把周期串解析成结构化」听起来是健壮，两个都是把驱动方的语义搬进 CLI。

看到 `infra` 不校验、不解析、不报无人听的事件——**那是对的，不是没写完。** 真要加校验，问一句：这条知识属于驱动方还是属于 CLI？属于驱动方的，别搬进来。
