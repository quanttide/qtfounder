# 文档审计路线图

从验证核心假设到阈值标定，分三步。每一步都有明确的停止条件，不通过就不往下走。

## 阶段零：先验证假设

在写代码之前先人肉验证。拿十篇文档，五篇手写、五篇 AI 生成，数一下三段式列表项占列表项的比例。

两组有明显分离（比如手写两成、AI 七成），规则成立，往下做。没有分离，说明核心直觉是错的，写代码也是白写。这一步成本半小时，收益是避免为错误假设实现一整套规则。

验证时顺带标定两件事：列表项字数的合理上限写在哪，以及哪些文档体裁本来就用条目写（规格、清单类文档不吃这一套）。

## 阶段一：列表层

在 `language` 里加一层列表判定，与表格层同构：

1. 契约加 `[list]` 段，至少三个字段：单项字数上限、三段式占比上限、列表项数下限（少于这个数不算结构块）。零值表示关闭，与其他层一致。
2. 判定层 `src/language/list.rs`，行级扫描即可，不需要引 Markdown AST：识别 `- ` 与 `1. ` 开头的块，逐项统计字数，匹配 `**加粗**：` 前缀的比例。
3. `Kind` 增加 `List`，`--kind list` 可单跑；报告沿用现有格式，行号指向列表起始行，建议写明整段重写为散文还是拆项。
4. 测试补齐真样本与反样本。反样本是关键：一段每项都加粗但确实是清单的文档，必须不报。

停止条件：十篇语料跑下来，误报集中在清单体文档且可以通过体裁排除解决。做不到就先别加规则。

## 阶段二：密度兜底

缺陷规则没命中、但整体仍像 AI 时，密度指标负责提示。两个指标：结构块占比（表格与列表字数除以总字数）、无散文率（没有过渡段落的连续结构块占总结构块的比例）。

这一层只提示，不单独触发修改，输出里明确标成嫌疑而不是错误。阈值先留空，跑语料再填。

## 阶段三：阈值标定

跑三十篇文档（手写与 AI 各十五），看密度分布，用分位数反推阈值，替换所有待标定的值。在那之前，工具的价值是观测，不是判定——凭空定的数字不算数。

## 风险

核心直觉错误的代价最大，所以把验证放在最前面；误报会让整份报告被忽略，所以只报 top N，规则可逐条关闭，体裁不适用的目录直接排除；规则膨胀的护栏是每加一条必须自带替代动作。

## 验收

拿真实文档跑一遍，报告贴回 AI，它能按位置改完，复跑达标。做不到这一条，规则就不算做完。
