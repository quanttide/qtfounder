# 文档审计

文档审计要解决的是排版惯性：AI 生成文档时，表格和列表成了默认形状，该讲成段落的地方也切成条目。它的目标不是统计器，而是 linter——报告必须告诉作者改哪一行、改成什么。

## 一条判据

只保留能闭环的东西。每条规则都要能回答同一个问题：它能不能让人知道改哪里、改成什么。答不上来的砍掉；只能统计的砍掉；能被更简单规则覆盖的砍掉；需要改写判断的（润色、重写）留给 AI，工具只提示。

## 五层

表格层从 `language` 整层迁来，其余四层是在 `docs` 上新增的。五层共用一份契约、同一个 `Finding` 形状与同一套报告。

表格查列数、行数、单元格长度、表头、稀疏度、两列表与排版表头。单列表格由 `flag_two_column` 与 `min_rows` 覆盖，单元格过长由 `max_cell_chars` 覆盖，所以路线图里的「退化表格」不必另写。

列表查两件事：单项过长，以及三段式占比过高。三段式指 `- **要点**：解释` 这种排法，人类写作很少整段这么排，密度过半基本可以判定整段需要重写。

密度查结构块占比与无散文率，只在前面两层都没命中时才看。它判的是整篇，出的是嫌疑，阈值默认关闭。

加粗查三件可数的事：每千字几处、一行几处、一处几个字。它不判加粗用在哪（那要读语义），只判重点是否满了；一整句加粗与一行三处重点都报。

分割线查全文处数，以及紧挨标题的那几条。前者是「横线当结构」，后者是纯装饰；分章该靠标题层级。

## 为什么从 `language` 拆出来

表格和列表是同一类介质——都在说「这段内容该不该是这个形状」，而 `language` 判的是文字本身：术语、句法、语用。混在一个命令里，`--kind` 的语义不一致，契约也混着两类介质。拆开之后 `language` 保留六个文字层，`docs` 管三个结构层，两边的契约、报告与测试互不牵连。

拆分时不留兼容层：`[table]` 段与 `Kind::Table` 从 `language` 删干净，`--kind table` 改由 `docs` 提供。留一份旧入口看起来平稳，实际会让两套口径慢慢走开。
