# 加一条验收标准

一条验收标准住在四个地方，加的时候要一起改。少改一处，它就会变成「文档里有、代码里没有」或者反过来。

## 一、一条检查住在四处

契约里放阈值或词表，有数值的必须有默认值，`0` 表示关闭。判定层在 `src/code/<layer>.rs` 或 `src/language/scan.rs`，只读 IR 与契约。测试要一条真样本加一条反样本，只有真样本的检查会「报得越多越对」。用户指南里说明它查什么、误报长什么样子。

## 二、先问三个问题

**它可数吗？** 可数可匹配的交规则引擎；要判语义的交给 `--sense` 或留给人。规则引擎便宜、可复跑；语义层贵、不稳，只用来兜底。

**误报时会怎样？** 误报的代价是用户开始忽略整份报告。所以每条检查要么零误报，要么明确标成「嫌疑」而不是「错误」。`language` 的句法层就是这么分的：超一百字标 ERROR，只超六十标嫌疑。

**谁能证伪它？** 写完必须有一个反样本能让它变绿。改不动判断结果的测试没有意义——`a_changed_contract_changes_the_verdict` 这条测试就是范例：把阈值从三层改到十层，深嵌套必须从三条降到零。

## 三、几种验收标准不该加

**重复上游工具已权威的检查**。`unused_imports` 判过一版，靠语法树自己判，把 `#[derive(Parser)]` 与 trait 方法全报成未用。rustc 零误报，重复做只会更差。

**判不了的**。逻辑跳跃、这段是谁写的、这篇该放哪一层——写进契约只会制造噪音。

**自己能对自己失效的**。所谓「查重」如果靠自己对比自己，永远报零。

## 四、改验收标准比加验收标准更常见

工具跑出六十四处命中时，真正该改的往往不是代码，而是阈值。判断顺序是：

1. 这条命中会影响读者吗？会 → 改代码；
2. 阈值是按谁的量法定的？不是你的 → 改阈值；
3. 改了阈值它就永远不报了？→ 这条验收标准本身错，删掉并留一条测试记录为什么删。
