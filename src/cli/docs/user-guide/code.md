# `qtfounder code` 用户指南

代码语用检查：判的不是语法错、不是风格、不是圈复杂度，而是**下一个维护者能不能看懂**。

## 一、四层查什么

| 层 | 问的问题 | 判据举例 |
|---|---|---|
| 词汇层 | 名字有信息量吗、名实相符吗 | 万能名 `data`／`temp`／`flag`；缩写 `ctx` 有两种读法；`user_map` 里装的是 `Vec`；仓库里 `get`／`fetch`／`load`／`read` 并存 |
| 句法层 | 读者要同时记住多少东西 | 嵌套超 3 层；函数超 60 行；参数超 5 个；认知负荷超 15；一行链 5 层调用 |
| 语篇层 | 一个文件在讲几件事 | 顶层定义超 15 个；一个 impl 方法超 15 个；`if false` 死分支 |
| 语用层 | 意图传达到了吗 | `handle` 不说对象；文档注释只把函数名说一遍；复杂分支零注释；`panic!("bad")` 不说怎么修 |

每条命中都写清违反 Grice 的哪一条原则（量／质／关系／方式）——这是它跟风格检查器的分别。

## 二、用法

```bash
cargo run -- code                 # 查当前目录
cargo run -- code src/cli         # 查指定目录
cargo run -- code src --layer pragmatic
cargo run -- code src --top 2     # 每类最多两条
cargo run -- code src --json
cargo run -- code src --rules my-rules.toml
```

装出来的二进制是 `qtfounder`，命令即 `qtfounder code ...`。

退出码：**0 无命中 / 1 有命中 / 2 有文件解析失败**。

## 二b、支持哪些语言

| 扩展名 | 提取器 | 解析方式 |
|---|---|---|
| `.rs` | `extract/rust_lang.rs`（专用） | `syn` |
| `.py` | `extract/python.rs`（专用） | `tree-sitter-python` |
| `.go` | `extract/tree_sitter_extractor.rs` + `specs::go()` | `tree-sitter-go` |
| `.ts` / `.mts` / `.cts` | 同上 + `specs::typescript()` | `tree-sitter-typescript` |
| `.dart` | 同上 + `specs::dart()` | `tree-sitter-dart` |

Go／TypeScript／Dart 共用同一份提取器，差异全在 `specs.rs` 的一份 `LangSpec` 里：函数节点名、名字与参数的下钻路径、嵌套节点集合、赋值节点与左右值字段、行注释前缀。**加这三个语言时判定层一行没改**，这就是这条路走通的证据。

### 三种语言暂时没有的三条验收标准

诚实列出来，别当成「没问题」：

- **调用链长度**——`chains` 留空，需要各语言的调用表达式结构，还没接；
- **文档复述**——`doc` 留空，注释与函数的关联方式三种语言各异，还没接；
- **名实不符**——`init_shape` 只记了右值节点类型，还没有构造器名归一。

其余七条（参数数、函数行数、嵌套深度、认知负荷、常量假条件、顶层定义数、名字检查）三种语言都已生效。

判定层不认语言：四层只读 `ir::Facts`。**加一个新语言只需写一个提取器，判定层一行不改**——这是这条路是否成立的唯一验收。

提取器要交出的事实就这些：函数名与参数个数、行范围、嵌套层数与认知负荷、方法调用链、绑定的名字与寿命、常量假条件、错误信息候选、文档注释、顶层定义数。

### 两个提取器的口径必须对齐

实测踩过的三处（都由对等测试抓出来，已修）：

- **函数参数也算绑定**——Python 侧第一版漏了，导致短名检查在两种语言上不一致；
- **调用链同一行只报一次**：一条链上每个节点都会被访问到，按行取最大链长；
- **「短命」只指标循环/推导式的目标本身**：循环体里的普通赋值在同一块内还要用，算长命。

`src/code/tests.rs` 里的 `both_languages_agree_on_every_sample` 就是守这条的：同一个缺陷两种语言各写一份，两边的 kind 集合必须相等。

### 与 Python 版 `qfc` 的已知差异

同一份 Python 代码，`qtfounder code` 与 `qfc` 报出的 **kind 集合相同**（实测十六对十七处），两处差在口径而非判据：

- **认知负荷公式**：Rust 版按嵌套深度加权累加；`qfc` 另把条件里的布尔并列、`break`／`continue` 也算进去，所以个别函数只有它报；
- **`too_many_defs` 的行号**：Rust 版记 0（整文件级），`qfc` 指到超线的那一行。

## 三、阈值在哪改

内嵌默认表在 `src/cli/data/rules/default-contract.toml`（编译进二进制），`--rules` 可覆盖。

- `[lexical]` —— 万能名词表、短名长度、白名单、缩写表、同义组；
- `[syntax]` —— 五个阈值：嵌套、行数、参数、认知负荷、链长；
- `[module]` —— 顶层定义数、impl 方法数；
- `[pragmatic]` —— 错误信息最短长度、复杂函数多少行才要求注释。

**名字好坏是项目口径**，所以词表在规则表里，不写死在代码里。

## 四、和 rustc 的分工：哪些判据**不做**

`unused_imports` 不判——rustc 的这项 lint 已经权威、零误报；靠 AST 自己判会漏掉 derive 宏与 trait 方法这两种用法（实测第一版把 `#[derive(Parser)]` 与 `use syn::spanned::Spanned` 全报成未用）。**重复做一遍只会更差。**

同理不做：语法错（rustc）、格式（rustfmt）、安全与性能（clippy 与其他工具）。

## 五、边界

不判逻辑对不对（测试的事）、不判「这段该不该存在」、不判类型标注是否最优。名字与结构判据都在**读者要不要记住它**这个前提下成立，不是审美偏好。

## 六、已知的判据近似

- 「短名」按作用域判：循环变量、闭包参数、match 绑定豁免——它们只活几行；
- 「认知负荷」按嵌套深度加权累加，是 Sonar 那套的近似，不是圈复杂度；
- 「名实不符」只看 `let` 初始化的构造器名字（`vec!`／`HashMap::new`／`String::from`），类型推断出来的情况看不到；
- 「文档复述」按词重合判，可能在极简文档上误报，所以只在文档短于 40 字时判。
