# `qtfounder docs` 用户指南

文档审计：判的不是语法和错别字，而是这段内容该不该是这个形状。表格和列表是 AI 生成文档时的默认形状，该讲成段落的地方也被切成一条条；加粗和分割线则是「满篇重点」与「横线分章」两类毛病；front matter 查的是标记本身说不说得清。

## 一、七层查什么

**表格**：列数、行数、单元格长度、有没有表头、空单元格比例、是不是两列表、表头是不是「说明」「备注」这类排版词。两列表本质是名词加一段解释，改成列表更自然；一格塞进一段话，说明这段该搬到正文。

**列表**：三项以上才算结构块。两类问题——单项过长（本该是段落）、三段式占比过高。三段式指 `- **要点**：解释` 这种排法，它是 AI 生成列表最稳定的指纹：人类写作很少整段这么排，密度过半基本可以判断整段要重写。

**密度**：结构块（表格与列表）字数占正文的比例、没有过渡段落的连续结构块占比。这一层只在前面两层都没命中时才看，出的是嫌疑不是错误，阈值默认关闭。

**加粗**：每千字几处、一行并列几处、一处几个字。整句加粗（超过三十字）与一行三处重点都报；满篇重点的密度按每千字计数，短于三百字不判。

**分割线**：全文超过三处即报；紧挨标题的横线单独报，因为那是装饰，分章该靠标题层级。首尾的 frontmatter 与代码块里的横线不算。

**Front matter**：有才算，没有不管。字段名不在 `[frontmatter] keys` 里报嫌疑；`status` 与署名 `type` 的取值不在表里报错。`genre`、`audience`、`topic` 是表达审计的画像，取值与 `write` 契约一致；写错报错，不写则用 default。

**日志模板**：只查日志正文，不查说明文件。文件名必须是 `YYYY-MM-DD.md`；写了标题就必须是 `# YYYY-MM-DD`，与文件名一致。不写标题也放行——手机直写时，日期在文件名上就够了。日志目录通常在 `[scope] exclude` 里，这一层单独跑，不受排除影响。

`status` 三档，同一条线上下走：`draft` 草稿、`pending` 待验证、`final` 定稿。AI 起草且说法未核的，落 `pending`。

谁写的用 MyST 的 `authors`，每条多一个 `type`：人的写 `human`，AI 的写 `agent`，机构写 `org`。模型名写在 `name` 里，像人署名一样；机构只认四个全名，照契约抄：量潮创始人、量潮科技、量潮实训基地、量潮创新联盟。不标 `type` 报错，`agent` 缺模型名报嫌疑，法人名写错报错。

```yaml
authors:
  - name: 张三
    type: human
  - name: DeepSeek V4.1 Flash
    type: agent
  - name: 量潮科技
    type: org
```

三档之外不另造近义词——`待验收`、`待验证`、`悬疑`、`疑惑` 都不是状态，前几个是 `pending` 的具体原因，最后一个该退回 `draft` 重写。

## 二、用法

```bash
cargo run -- docs docs                 # 审文档站的 16 个文件
cargo run -- docs docs --kind list     # 只看列表
cargo run -- docs docs --kind frontmatter  # 只看 front matter
cargo run -- docs docs --kind journal  # 只看日志模板
cargo run -- docs docs --kind bold     # 只看加粗
cargo run -- docs docs --stats         # 只打密度数字，不下结论
cargo run -- docs docs --json
cargo run -- docs format docs/user-guide/docs.md  # 单篇的格式状态
cargo run -- docs format docs --top 10            # 一目录：按格式元素数排序
cargo run -- docs check                # 技能索引与目录比对
```

退出码：**0 无命中 / 1 有命中 / 2 契约或文件读不了**。

## 三、格式状态（`docs format`）

数的是格式元素，判的还是同一套审计：先给数，再给命中——有没有滥用格式先看数，该改哪一处再看审计。

```bash
cargo run -- docs format docs/user-guide/docs.md   # 单篇：逐项列出
cargo run -- docs format docs --top 10             # 一目录：按元素数从多到少
cargo run -- docs format docs --json               # 数字给机器读
```

单篇逐项列出：正文字数，标题（另标一级个数与最深层级）、表格张数与行数、列表块数与项数、加粗处数、分割线条数、块引用段数、代码块个数，最后一行是格式元素合计。目录模式每个文件一行，按元素数从多到少排，最多列 `--top` 个，末尾给合计。

元素 = 标题 + 表格 + 列表 + 加粗 + 分割线 + 块引用 + 代码块，这七类怎么算照《量潮科技文档格式章程》第四条。

状态与审计共用同一处识别：状态说两条分割线，审计认的就是这两条；`--kind` 只过滤审计那一段，状态永远全数——数错了就没法拿数下结论。

## 四、密度观测

阈值还没标定，`[density]` 两个上限默认是 0，也就是只观测不判断。加 `--stats` 会按块占比从高到低列出每篇的字数、结构块数与两个比例，用来给语料标定取值。标定不靠拍脑袋：跑两组已知来源的文档，看分布再回填，方法见开发指南的[文档审计路线图](../dev-guide/docs/roadmap.md)。

## 五、`docs check`

比对 `.agents/skills/` 下实际存在的技能与 `AGENTS.md`、`CONTRIBUTING.md` 里引用的名字，报两类：目录里有但索引没写、索引写了但目录里没有。从子目录跑也能找到仓根的技能目录。

## 六、契约在哪

`src/cli/src/docs/default-contract.toml`，查找顺序与 `language` 那份一样，也不内置兜底。装到本地时把契约放到 `~/.config/qtfounder/docs/default-contract.toml`。

## 七、已知边界

**清单体文档会被列表层命中。** 规格、教程本来就该用列表写，三段式也常见。这类误报靠目录排除解决，不靠放宽阈值——阈值一松，说明文里的滥用就漏了。

**密度阈值默认关闭。** 在标定之前它只出数字，不出结论。

**待办项按普通列表项算。** `- [ ] 做某事` 会被当成一条，过长的照样报。

**代码块里的表格、列表与横线不参与。** 教程里贴的样例不检查，规则只对正文生效。

**状态只数七类元素。** 链接与引号不数：链接是内容不是形状，引号数出来噪音大（代码与 URL 里的引号分不开）。setext 标题（`标题` 下面划 `---`）按正文行算，既不算标题也不算分割线。
