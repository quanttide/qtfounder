# 代码审查：从事实面看功能

## 你是什么：功能审查，不是语言学检查

`qtfounder code review` 判的是**功能还对不对得上**，不是代码写得好不好。命名、注释、读感那些语言学特点归 `language`（它同时判自然语言与编程语言的语言学特点），别在这儿重复。

你面对的是一段没有功能声明的代码。你的活：从事实面（有哪些函数、哪里复杂、哪里死了、报错会怎样）反推它**该做什么**，再看还对不对得上。适用于接手遗留代码、重构前摸底、判断边界覆盖没。

## 功能的四问

推功能预期就按这四问——判的是「它该做什么」，不是「它怎么写」：

| 问 | 要回答的问题 |
|:--|:--|
| 解决什么 | 这段代码要解决的问题是什么，一句话说清 |
| 承诺什么 | 对外承诺的行为：输入什么、吐出什么、失败时怎样 |
| 边界覆盖没 | 空、错、并发、规模上去之后，覆盖了没 |
| 哪没验证 | 没有测试、没有断言、没有真实调用走过的地方 |

## 前置

```bash
cargo build --release && install -m755 target/release/qtfounder ~/.local/bin/qtfounder
qtfounder code review src/meta --example   # 能出骨架说明装的是新版
```

## 审查工作流

### 第一步：拿骨架与功能锚点

```bash
qtfounder code review <目标>              # 报告骨架 + 事实面的功能锚点（带 file:line）
qtfounder code review <目标> --json       # 给脚本读
```

命令出四节骨架（结论、功能预期、清单与锚点、建议）与六条交付纪律。**清单里那批带 `file:line` 的是从事实面取来的功能锚点**——函数清单、恒假条件、复杂度过高、错误信息，直接可用；`--example` 才连纪律的例子一起打。

### 第二步：对着函数清单问「这事归它管吗」

逐个函数过一遍清单：

- 它做的事对得上名字吗；
- 它的输入输出边界清楚吗、失败时会怎样；
- 有没有更该拆出来的一件事被塞在了别处。

这些是**功能预期**的核对，不是命名好坏的评判——命名归 `language`。

### 第三步：追恒假条件与错误路径

```bash
git log --oneline -- <目标文件或目录>
git log -p -- <目标文件>
```

锚点里的 `dead_branch`（恒假条件）是最硬的功能信号：这段永远不会执行，先确认是漏了分支还是死了的代码。`thin_error`（错误信息太短）是失败路径的信号：用户只知道错了，不知道哪里错、怎么办。

### 第四步：按四问归纳，逐条对锚点

按四问推功能预期，然后拿第二、三步的发现去对：

- **与承诺矛盾** —— 说好的行为，代码里没做到；
- **边界漏了** —— 空、错、并发没覆盖，规模上去会崩；
- **没验证** —— 关键路径没有测试或断言，功能对不对无从知道。

写不出 `file:line` 锚点的发现**不写**。锚点写不出，说明这条还只是感觉，进不了清单。

### 第五步：写报告，人拍板

交付物是报告，不是过程记录。写完交给用户，**功能该是什么由人判断**——模型不知道这段代码本该解决什么问题，它推的「功能对不对」是候选，不是实测。

## 报告格式

```text
# 功能审查：<目标>

## 结论
<一到三句：这段代码该解决什么、功能上最该先核的一件事>

## 功能预期
- 解决什么：……
- 承诺什么：……
- 边界覆盖没：……
- 哪没验证：……

## 清单与锚点（按严重度排序）
1. [严重] <一句话问题> — <file:line>
   与承诺的关系：<矛盾 / 边界漏了 / 没验证>
2. [中] ……

## 建议
<可删项（死代码）、需与作者确认的行为、缺的测试与断言>
```

纪律六条在契约 `[[review]]` 里，命令每轮都会打给你：结论先行、锚点必备、一条一个发现、按严重度排、只给候选、不写过程。

## 示例

**题目**：审 `src/meta`，它没写过功能声明。

跑 `qtfounder code review src/meta`，从事实面给出一批功能锚点（函数清单、复杂度过高、恒假条件）。这些是线索不是结论，先放着。

第二步对着函数清单：`judge` 跨 148 行、认知负荷高（锚点 `src/meta/classify.rs:116`，实测于 2026-10-30）——这么长的函数，边界对不对最难核。

第三步追恒假与错误路径：`contract.rs` 有一段被注释掉的校验，等于某个分支永远走不到。

第四步按四问推功能预期，「承诺什么」写的是「给一条内容判它的归位，不搬文件」。对锚点：

1. `[严重] judge 跨 148 行，边界与错误路径难核 — src/meta/classify.rs:116` 与承诺的关系：边界漏了——超长函数里空输入、打平这些路径容易漏。
2. `[中] 校验被注释，某个分支永远走不到 — src/meta/contract.rs` 与承诺的关系：没验证——这段校验还在不在承诺里，得作者确认。

第五步写报告交出去。**不说「建议立即重构 judge」**——那是用户的判断，只给锚点与关系。

## 记使用体会

审完，把你自己（或不同使用者）的真实判断记下来，一人一条。同一处代码可以有多个人各记各的，下次审时摊开看。

```bash
echo "函数清单很有用，但恒假那处我没看出是不是漏了分支。" \
  | qtfounder code review <目标> --record --user alice
qtfounder code review <目标> --experiences        # 列出所有人的体会
qtfounder code review <目标> --experiences --json  # 给脚本读
```

体会与 `write review` 的读者体会落在同一处（`<数据根>/review/experiences.json`），靠 domain 区分代码审查与读者评审。体会是人的话，机器不代笔、不改写。报告里有一节「使用体会」，记过的会摊在那儿。

## 排错

- **`契约里没有 [[review]]`** —— 装的是旧二进制，跑前置那两条重建重装；或 `--rules` 指了一份没写审查段的自定契约。
- **锚点一处都没有** —— 目标下没有认得的代码文件（只接 rs/py/go/ts/dart），或都是简单函数没触发阈值。不是审查过了，是机械层没给线索；这时清单只能靠真读，写不出锚点的发现照旧不写。
- **清单长到没法看** —— 没按严重度收。只列高价值的若干条，其余归入「其他」；清单一长，重要的就沉到底。
- **每条都想写「建议重构」** —— 那是把判断塞回报告。锚点与关系写清，怎么处置留给用户。
- **读感、命名的问题也往这儿写** —— 那是 `language` 的活。这边只判功能对不对。
- **`记一条体会要指明是谁的`** —— `--record` 没带 `--user`。体会带人，多个人各记各的，缺了 user 就不知道是谁的判断。
