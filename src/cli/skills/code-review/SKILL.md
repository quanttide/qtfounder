# 代码审查：从代码反推意图

## 你是什么：反向流程

`code-refactor` 是正向——先有意图，再由意图推代码。**这边是反向**：面对一坨没有意图声明的代码，还原写它时的意图，据此判断哪里偏了。适用于审查既有代码、接手遗留代码、为重构做前置分析。

## 意图的五层

与 `code-refactor` 同一套，不多不少：

| 层 | 要回答的问题 |
|:--|:--|
| 核心目标 | 这一坨本质上要干什么，一句话说清 |
| 边界 | 什么它不干 |
| 约束 | 什么条件必须满足 |
| 已知假设 | 基于什么前提在做事 |
| 不确定性 | 哪些地方还没想清楚 |

## 前置

```bash
cargo build --release && install -m755 target/release/qtfounder ~/.local/bin/qtfounder
qtfounder code review src/meta --example   # 能出骨架说明装的是新版
```

## 审查工作流

### 第一步：拿骨架与锚点

```bash
qtfounder code review <目标>              # 报告骨架 + 语用命中的 file:line 锚点
qtfounder code review <目标> --layer pragmatic   # 只取某几层的命中
qtfounder code review <目标> --json       # 给脚本读
```

命令出四节骨架（结论、意图假设、偏移清单、建议）与六条交付纪律。**偏移清单里那批带 `file:line` 的是机械层给的锚点**，直接可用；`--example` 才连纪律的例子一起打。

### 第二步：宏观扫描，找「不自然」

快速浏览，标出所有让你产生「为什么这样」疑问的地方：

- 奇怪的数据结构选择；
- 多余的抽象层；
- 注释掉的代码块；
- 过度通用的接口；
- 重复但略有不同的逻辑。

这些不是坏代码，是**意图偏移的化石**——每一处都对应一次「当时不知道该怎么做，先这么写了」。

### 第三步：用 git 历史还原时间线

```bash
git log --oneline -- <目标文件或目录>
git log -p -- <目标文件>
```

三类提交最说明问题：早期提交最接近原始意图；大块新增可能是新意图注入；紧急修复通常意味着意图与现实打架。

### 第四步：反推意图，逐条对锚点

按五层反推，然后拿第二、三步的发现去对：

- **与意图矛盾** —— 意图说不干，代码里干了；
- **越界新增** —— 没人要求，也没写进哪一层；
- **不服务意图** —— 既不服务核心目标，也不在边界内。

写不出 `file:line` 锚点的发现**不写**。锚点写不出，说明这条还只是感觉，进不了清单。

### 第五步：写报告，人拍板

交付物是报告，不是过程记录。写完交给用户，**还原成不成立由人判断**——模型会过度合理化，给每个奇怪的地方都编一个像样的解释。

## 报告格式

```text
# 意图审查：<目标>

## 结论
<一到三句：最可能的意图、整体偏移程度、最该先处理的一件事>

## 意图假设
- 核心目标：……
- 边界：……
- 约束：……
- 已知假设：……
- 不确定性：……

## 偏移清单（按严重度排序）
1. [严重] <一句话问题> — <file:line>
   与意图的关系：<矛盾 / 越界新增 / 不服务意图>
2. [中] ……

## 建议
<可删项、需与作者确认项、下一步>
```

纪律六条在契约 `[[review]]` 里，命令每轮都会打给你：结论先行、锚点必备、一条一个发现、按严重度排、只给候选、不写过程。

## 示例

**题目**：审 `src/meta`，它没写过意图声明。

跑 `qtfounder code review src/meta`，机械层给出一批锚点（调用链过长、名不副实、函数太长）。这些是线索不是结论，先放着。

第二步扫出三处不自然：锚点里 `judge` 跨 148 行却只有一处注释（`src/meta/classify.rs:116`，实测于 2026-10-30）；`contract.rs` 有一段被注释掉的校验；`axiom.rs` 的 `print_domain` 两个分支只差一行。

第三步查 git：`judge` 是三次提交叠出来的，每次加一段判断。

第四步反推五层，其中「边界」写的是「只判归位，不搬文件」。对锚点：

1. `[严重] judge 三次叠加，边界已写不进一句话 — src/meta/classify.rs:116` 与意图的关系：矛盾——每加一段都在突破上一轮的边界。
2. `[中] print_domain 两分支只差一行 — src/meta/axiom.rs:33` 与意图的关系：越界新增。

第五步写报告交出去。**不说「建议立即重构 judge」**——那是用户的判断，只给锚点与关系。

## 记使用体会

审完，把你自己（或不同使用者）的真实判断记下来，一人一条。同一处代码可以有多个人各记各的，下次审时摊开看。

```bash
echo "这份骨架把「判断归人」守住了，但意图假设五层得我自己填。" \
  | qtfounder code review <目标> --record --user alice
qtfounder code review <目标> --experiences        # 列出所有人的体会
qtfounder code review <目标> --experiences --json  # 给脚本读
```

体会与 `write review` 的读者体会落在同一处（`<数据根>/review/experiences.json`），靠 domain 区分代码审查与读者评审。体会是人的话，机器不代笔、不改写。报告里有一节「使用体会」，记过的会摊在那儿。

## 排错

- **`契约里没有 [[review]]`** —— 装的是旧二进制，跑前置那两条重建重装；或 `--rules` 指了一份没写审查段的自定契约。
- **锚点一处都没有** —— 语用检查零命中。不是审查过了，是机械层没给线索；这时偏移清单只能靠反推，写不出锚点的发现照旧不写。
- **清单长到没法看** —— 没按严重度收。只列高价值的若干条，其余归入「其他」；清单一长，重要的就沉到底。
- **每条都想写「建议重构」** —— 那是把判断塞回报告。锚点与关系写清，怎么处置留给用户。
- **`记一条体会要指明是谁的`** —— `--record` 没带 `--user`。体会带人，多个人各记各的，缺了 user 就不知道是谁的判断。
