# 术语治理

禁用词不是「这些词不好」，是「这些词不属于这里」。治理要做的不是通篇换词，是逐处判它在这个语境里算不算错，再把整批落在同一次改动里。

规则在哪：章程写边界与例外（`docs/bylaw/language/`），规格写语境的定义（`docs/specification/language/context.md`），词表与替代写法在工具契约（`apps/qtfounder/src/cli/src/language/default-contract.toml`）。这份 Skill 只写怎么动手。

## 何时用

- 体检报告点了一个词，要清一轮
- 想确认某个词现在还能不能用
- 新词要入库，或旧词要出库
- 写完一批文档，想自查用词

## 前提

三样东西要在位，缺一样就别开工：

```bash
qtfounder audit        # 体检：每期只说一处
git config core.hooksPath   # 闸门：应是 .githooks
cat apps/qtfounder/src/cli/src/language/default-contract.toml | head -40
```

闸门只拦新增用词。它保证这一轮不会改出新错，也让「一轮一个词」有边界。

## 一轮六步

### 第一步：取真实命中

体检只报一处，取全量要用语言审计的 JSON：

```bash
qtfounder language . --rules apps/qtfounder/src/cli/src/language/default-contract.toml --json \
  > /tmp/lang.json
```

只留同时满足三条的：`severity` 是 `error`、`verdict` 是 `real`、`line` 不为 0。带 `「」` 的提及是讨论词本身，不算使用。

拿到清单先做两件事。

一是按文件分组，看它落在哪些仓。二是每处都读上下文，读的是 `grep` 的结果，不是扫描器的摘要：

```bash
grep -rn "<词>" --include='*.md' .
```

扫描器一行只报第一处。同一行出现两次、或者同一个词有别的写法，只有 `grep` 看得见。

### 第二步：先判该不该改

不是所有命中都该换。三种情况要停下来讨论：

- **正常中文占多数**：比如「依据」写「执行依据」，这是日常用法。数一遍，正常用法过半就提出库，改章程与契约，别硬换。
- **指真实对象**：词是某个东西的名字时，要动的是名字，得连命令行、skill、档案一起改。
- **别的领域的术语**：比如认知行为疗法里的 `正反证据`。换成近义词会失真，这时该缩小词的适用面，或在契约里写例外。

判完再动手。一轮只清一个词。

### 第三步：按语境定替换

同一个词在不同位置换法不同。分五类看：

| 位置 | 怎么换 | 例 |
|---|---|---|
| 动词 | 换成本义的动词 | `判定它够不够好` → `判断它够不够好` |
| 名词指代 | 换成具体的量词或对象 | `三个条目` → `三条` `三项` |
| 标题与小标题 | 说清这一节干什么 | `判定口径` → `怎么判` |
| 表头 | 换成读者要查的那件事 | 「判定」→「怎么判」 |
| 组件名 | 整批改名，不留豁免 | `判定层` → `判断层` |

组件名要一并改文档与代码注释。留一条豁免的代价是它每轮都被报出来，早晚还得改。

### 第四步：批量改并断言

写一次性脚本，每条替换都断言命中次数：

```python
if text.count(old) != expected:
    raise SystemExit(f"{path}: 「{old}」命中 {count} 次，预期 {expected} 次")
```

脚本放实验室仓（`examples/quanttide-founder-lab/examples/`），跑完再删，别写临时目录。

同一段样板文字散在很多篇里时（比如各篇开头的来源说明），用一个循环统一改，别一篇篇手敲。

### 第五步：两套审计复查

```bash
qtfounder language . --rules apps/qtfounder/src/cli/src/language/default-contract.toml --json
qtfounder docs . --rules apps/qtfounder/src/cli/src/docs/default-contract.toml --json
qtfounder audit
```

要看三个数：这个词是否归零、错误总数是否按预期下降、嫌疑是否没有异常增加。如果总数没降够，多半是有漏网的同义词与后缀写法，回到 `grep`。

### 第六步：分仓提交，写回路线图

一处内容散在多个仓时，每个仓一条提交，再回主仓更新指针。

路线图记一笔：这一期清完，下一期从哪个词开始。变更写进该仓的 `CHANGELOG`。

## 坑

**`git add -A` 会带上别人的改动。** 子模块里常有用户自己没提交的文件，一律用明确路径暂存，提交前看一眼 `git status`。

**闸门会拦下自己写的说明。** 写治理清单时描述被禁词，必须用 `「」` 或反引号包住，否则判成使用。

**「」不是万能豁免。** 引用整句时（比如 `加语言不改判定`），里面的词仍可能被判为使用。改掉比争论判定更省事。

**契约查找会落到用户目录。** 在主仓根跑命令时，如果仓里没有 `src/cli/src/...`，会取 `~/.config` 的旧文件。差异表现为总数对不上，先核对契约路径再加 `--rules`。

**别在两处写同一份清单。** 现状与数量写在路线图，方法与命令写在这里，章程与契约只写规则。

## 收尾自查

1. 这个词的真实命中归零了吗？
2. 错误总数按预期下降了吗？
3. 有没有把正常用法一起改掉？
4. 组件名、表头、标题都连着改了吗？
5. 每个仓都提交并推送了吗？主仓指针更新了吗？
6. 路线图写清下一期了吗？
