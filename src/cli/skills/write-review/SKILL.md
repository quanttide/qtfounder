# 文档评审：从读者角度，不从作者角度

## 你是什么：读者，不是编辑

`write-express` 是正向——先看文字本身哪里空、哪里喊口号，再重排。**这边是反向**：你坐到读者的位置上，带着读者的问题把这篇读一遍，记录他在哪停下、走神、回读、合上。你不替作者改稿，不评价「写得好不好」——你只回答「读者读完带走了什么」。

视角一旦滑回作者侧（「这里该拆成两段」「这句应换个说法」），报告就成了改稿意见，读者那一刻的真实反应反而被盖住。**这是本评审唯一不能破的纪律。**

## 四个问题

与 `code review` 的五层意图对称，但视角锁在读者侧：

| 层 | 要回答的问题 |
|:--|:--|
| 读者是谁 | 带着什么问题来读，愿意花多久 |
| 读者要什么 | 想从这篇拿走的一个判断或一个动作 |
| 读者卡在哪 | 哪一句、哪一节让他停下、走神、回读 |
| 读者带走什么 | 合上这篇，他记得的、能做的还剩多少 |

## 前置

```bash
cargo build --release && install -m755 target/release/qtfounder ~/.local/bin/qtfounder
qtfounder write review docs/index.md   # 能出骨架说明装的是新版
```

## 评审工作流

### 第一步：拿骨架与卡点

```bash
qtfounder write review <目标>             # 评审骨架 + 表达审计命中的 file:line 卡点
qtfounder write review <目标> --audience <读者>   # 指定读者画像，卡点更贴人
qtfounder write review <目标> --json      # 给脚本读
```

命令出四节骨架（结论、读者视角、卡点清单、建议）与六条交付纪律。**卡点清单里那批带 `file:line` 的是表达审计给的位置**——空话、口号、指路、结构这些让读者停下的地方，机器先指位置。`--example` 才连纪律的例子一起打。

### 第二步：真读一遍，记读者的停顿

骨架是入口不是结论。你以读者身份通读，标出所有让你停下、回读、走神的地方：

- 这个词我不认识，得往前翻定义；
- 这一段绕回来了，我不知道它要说什么；
- 读到这我忘了前面的问题是什么；
- 这句「见某某文档」——我手上没有那份文档，读到这就断了。

这些是**读者的卡点**，不是文章的缺陷。写法上只写「读者读到这会……」，不写「作者应改成……」。

### 第三步：按四个问题归纳

把第二步的停顿归到四问里：读者是谁、他要什么、他在哪卡住、他带走什么。**写不出具体位置的卡点不写**——位置写不出，说明这条还只是感觉，进不了清单。

### 第四步：出评审，人拍板

交付物是评审，不是过程记录。写完交给用户，**读者会怎么反应由人判断**——模型不知道真实的读者是谁，它推的「读者会怎样」是候选，不是实测。

## 评审格式

```text
# 读者评审：<目标>

## 结论
<一到三句：读者读完最可能的感受、最卡的一处、最该先补的一件事>

## 读者视角
- 读者是谁：……
- 读者要什么：……
- 读者卡在哪：……
- 读者带走什么：……

## 卡点清单（按读者停下的先后排）
1. [严重] <读者在哪停下> — <file:line>
   读者视角：<读不懂 / 走神 / 误解 / 找不到>
2. [中] ……

## 建议
<从读者角度：哪一处补一句背景、哪一节该挪后、哪一段可以整段删>
```

纪律六条在契约 `[[review]]` 里，命令每轮都会打给你：结论先行、锚点必备、读者不作者、一条一个卡点、只给候选、不写过程。

## 记读者体会

评完，把你自己（或不同读者）的真实判断记下来，一人一条。同一篇可以有多个读者各记各的，下次评审时摊开看。

```bash
echo "L14 那句我没读懂，回读了一遍才知道是说动了别人的配置。" \
  | qtfounder write review <目标> --record --user carol
qtfounder write review <目标> --experiences        # 列出所有读者的体会
qtfounder write review <目标> --experiences --json  # 给脚本读
```

体会与 `code review` 的使用体会落在同一处（`<数据根>/review/experiences.json`），靠 domain 区分读者评审与代码审查。体会是人的话，机器不代笔、不改写。

## 示例

**题目**：评 `docs/tutorial/getting-started.md`，它要给新读者上手。

跑 `qtfounder write review docs/tutorial/getting-started.md`，表达审计给出三处卡点（一段到底、两处指路让读者去看别的文档）。

第二步以读者身份通读：第三节假设读者已装好 CLI，但新读者没装，读到 `qtfounder infra add` 就停下；「事件总线」第一次出现没解释，我回读了上一段。

第三步归进四问。其中「读者是谁」写的是「会用 git 但没碰过本工具的产品经理」。

第四步出评审，卡点写成：

1. `[严重] 第三节假设 CLI 已装，新读者读到命令就停 — getting-started.md:L58` 读者视角：找不到安装步骤，只能往下猜。
2. `[中] 「事件总线」首现无解释 — getting-started.md:L23` 读者视角：回读上一段，仍不知道它是什么。

**不说「建议在第三节前补一节安装说明」**——那是作者的判断，只写读者在哪停下、为什么。

## 排错

- **`契约里没有 [[review]]`** —— 装的是旧二进制，跑前置那两条重建重装；或 `--rules` 指了一份没写评审段的自定契约。
- **卡点一处都没有** —— 表达审计零命中。不是评审过了，是机器没给位置；这时卡点清单只能靠真读一遍，写不出位置的发现照旧不写。
- **写着写着变成改稿意见** —— 视角滑回作者侧了。通读一遍，把「作者应……」全换成「读者读到这会……」。
- **清单长到没法看** —— 没按读者停下的先后收。只列高价值的若干条，其余归入「其他」；清单一长，重要的就沉到底。
